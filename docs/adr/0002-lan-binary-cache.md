# 사내망 바이너리 캐시: nix 파일 캐시를 nginx 컨테이너로 내보낸다

첫 `nix develop`은 12–18분 걸린다(ADR 0001, P8 클린룸). 대부분은 공개 캐시에 없는 CI 버전 도구(perl,
git, bison, indent, astyle)를 소스에서 빌드하는 시간이다. 나머지는 cache.nixos.org에서 받는 시간이다.
ADR 0001 D12는 콜드 스타트가 1시간을 넘을 때만 바이너리 캐시를 다시 논의하기로 했다. 그러나 사용자는
밖에서 받는 것도 느리다는 이유로, 사내 서버에 캐시를 두기로 했다(2026-09-30).

## D1 — 대상: 사내망

이 캐시는 사내망 머신만 쓴다. 사내 서버와 그 위의 컨테이너, 그리고 VPN으로 들어온 머신이다. 밖의
머신은 이 캐시에 닿지 않으므로, 지금처럼 공개 캐시와 소스 빌드로 준비한다.

## D2 — 형식: nix 파일 캐시와 정적 웹 서버

- **결정:** nix의 파일 바이너리 캐시를 디렉터리에 만들고, 그 디렉터리를 정적 웹 서버로 내보낸다. 캐시는
  서명된 `.narinfo`와 zstd로 압축한 NAR로 이뤄진다.
  - 서버에는 nix가 필요 없다.
  - 디렉터리를 비우고 다시 채우면 초기화된다.
- **고려한 것:**
  - Cachix 같은 외부 호스팅: 밖에서 받는 것이 느리다는 문제가 그대로 남는다.
  - nix-serve, harmonia: 서버에 nix와 그 스토어가 있어야 한다.
  - attic: 다중 사용자와 중복 제거를 주지만 이 규모에는 과하다.

## D3 — 범위: 새 환경이 받거나 빌드할 것 전부

- 다음 세 가지를 올린다.
  - `nix develop`의 입력.
  - `just build`가 쓰는 CUBRID derivation의 빌드 입력. 봉인 입력도 여기에 든다.
  - flake 입력의 소스: nixpkgs, CTP, 기본 엔진 소스.
- nixpkgs 것도 올린다. 그래서 캐시가 닿는 머신은 공개 캐시에 가지 않는다.
- 캐시의 우선순위는 30이다. cache.nixos.org는 40이고, nix는 숫자가 작은 캐시에 먼저 묻는다.
- 사용자의 워크트리로 빌드한 CUBRID 설치본은 올리지 않는다. 소스마다 스토어 경로가 달라서 다시 쓰이지
  않는다.

## D4 — 서버: 자기 LAN IP를 가진 ipvlan 컨테이너

- **결정:** nginx 컨테이너를 podman 호스트 위에 ipvlan 네트워크로 띄워 자기 LAN IP를 준다.
  - 캐시 디렉터리는 읽기 전용으로 `/cache`에 마운트한다.
  - 이미지는 flake의 `cache-server-image`다. nixpkgs의 nginx를 dockerTools로 묶은 것이라 레지스트리
    없이 만들고, `podman load`로 올린다.
- **이유:** ipvlan 컨테이너는 자기 호스트의 IP에 닿지 못한다. 개발 컨테이너에서는 호스트로 ARP조차
  되지 않았다.
  - 그래서 호스트에서 캐시를 서비스하면, 같은 호스트의 개발 컨테이너들이 그 캐시를 쓸 수 없다.
  - ipvlan 컨테이너끼리는 닿고, 다른 LAN 머신에서도 닿는다.
- **디렉터리:** 캐시 디렉터리는 개발 컨테이너가 마운트한 호스트의 SSD에 둔다. 개발 컨테이너가
  `just cache-push`로 채우고, 서버 컨테이너는 같은 디렉터리를 읽는다. 네트워크로 올릴 일이 없다.

## D5 — 서명 키

- 키 이름은 `cubrid-nix-cache-1`이다.
- 비밀 키는 채우는 쪽의 `~/.config/cubrid-nix/cache-key.secret`(권한 600)에만 있다. 공개 키는 README에
  있다.
- 키는 이렇게 만든다.
  - 비밀 키: `nix key generate-secret --key-name cubrid-nix-cache-1 > ~/.config/cubrid-nix/cache-key.secret`
  - 공개 키: `nix key convert-secret-to-public < ~/.config/cubrid-nix/cache-key.secret`
- 비밀 키를 잃으면 새 이름(`cubrid-nix-cache-2`)의 키로 빈 디렉터리를 다시 채운다. 그리고 사용자의
  `nix.conf`에 새 공개 키를 준다.

## D6 — 갱신

- `flake.lock`이나 `nix/`가 바뀌면 `just cache-push <디렉터리>`를 다시 돌린다. 도구 버전, CI 스냅샷, 기본
  엔진 입력이 바뀌는 경우다.
- 이미 있는 경로는 건너뛴다.
- 오래된 경로는 지우지 않는다. 캐시가 너무 커지면 디렉터리를 비우고 다시 채운다.
- 올리기 전에 스토어 경로의 내용 해시를 검사한다. 올린 뒤에는 캐시의 모든 경로를 공개 키로 검증한다.
  클라이언트가 받을 것을 그대로 확인하는 셈이다.

## 검증 (2026-09-30, 개발 컨테이너)

- **캐시:** 경로 321개, 압축 후 938MB(NAR 2.26GiB)다. 호스트 스토어에 모두 있던 상태에서 채우는 데
  24초 걸렸다. 서버 이미지는 16MB다.
- **콜드 스타트:** 이미지를 개발 컨테이너의 podman으로 띄우고, 캐시를 켠 클린룸에서 쟀다.
  - 전체는 270초였다. 캐시 없이 잰 두 번은 719초와 1109초였다.
  - `nix develop` 단계는 23초였다. 캐시 없이는 595초와 932초였다.
  - 로컬에서 빌드한 것은 봉인 입력과 시드처럼 몇 초에 끝나는 derivation 7개뿐이다.
  - nixpkgs와 CTP 소스도 캐시에서 받았다. GitHub에는 엔진과 테스트케이스 clone만 갔다.
  - 이때 호스트가 바빠서(load 190) nix 설치와 clone은 평소보다 느렸다.
- **찾은 결함:** 캐시의 gdb 경로가 해시 검사에 걸려, 클라이언트가 그 경로를 공개 캐시에서 받았다.
  - 원인은 호스트 스토어의 gdb 경로에 생긴 `.pyc` 22개다. README 검증에서 gdb를 user namespace의
    root로 돌렸을 때 gdb의 Python이 자기 스토어 경로에 썼다.
  - 이제 gdb 래퍼가 `PYTHONDONTWRITEBYTECODE=1`을 둔다.
  - `just cache-push`는 위의 두 검사를 한다.
- **고친 뒤:** 호스트의 gdb 경로를 복구하고 그 항목을 다시 채웠다. 캐시는 경로 329개, 940MB가 됐다.
  - 새 클라이언트가 HTTP로 받아 보니 모든 경로의 해시와 서명이 맞았다.
  - 래퍼로 gdb를 user namespace의 root로 돌린 뒤에도 gdb 경로는 그대로였다.
- **운영 주의:** 캐시에 있던 경로의 항목을 지우고 다시 채우면, 그 narinfo를 이미 받아 둔 클라이언트는
  옛 NAR을 찾다가 404를 받는다. nix는 받은 narinfo를 30일 기억한다.
  - 그런 클라이언트는 `~/.cache/nix/binary-cache-v*.sqlite`를 지운다.
  - 이번 복구는 서버를 띄우기 전이라 해당하는 클라이언트가 없다.
